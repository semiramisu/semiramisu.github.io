# Codexの最小課金プランで個人Webアプリはどこまで作れるか

## OrcaとCloudflareで、遠距離カップル向けの予定・思い出管理アプリを作った

> この記事は、GPT-6-Lunaを使って構成・文章を作成しています。実装作業ではCodexを使いました。内容の確認、外部サービスの設定、画面の確認は人間が行っています。
>
> 掲載する画面は、個人情報を含まないローカルの隔離デモ環境で撮影します。表示名、メールアドレス、予定、場所、旅行、アルバムURLはすべて架空のサンプルです。

## はじめに

今回の目的は、個人で契約できるCodexの最小課金プランを使い、自分でコードを書かずに、どこまで個人向けWebアプリを作れるかを試すことでした。

題材には、遠距離で暮らす2人のための共有アプリを選びました。2人の予定、これから行きたい場所、訪れた場所、写真アルバム、旅行計画をひとつにまとめるアプリです。

単にアプリを作るだけではなく、次の点も確認しました。

- 自然言語で要望を伝えるだけで機能を増やせるか
- UIの修正やスマートフォン対応までAIに任せられるか
- Google Calendar、天気、地図などの外部サービスを組み合わせられるか
- Cloudflareの無料枠で個人利用のアプリを運用できるか
- 本番データを使わずに画面や動画を紹介できるか

## 先に結論：コードを書く量は大きく減らせる

今回の開発では、Codexに次の作業を依頼しました。

- 既存コードの調査
- データベースの変更
- APIと画面の実装
- スマートフォン向けUIの修正
- Google Calendar連携
- 天気予報と地図の追加
- テストと型チェック
- 画面を確認した後の細かな修正

人間側は、作りたい機能や優先順位を決め、実際の画面を見て修正点を伝えました。また、Google CloudやCloudflareのアカウント設定、OAuth同意画面、Secrets登録、本番環境の確認は本人が行う必要があります。

「自分でコードを書かない」というのは、何も考えずに完成するという意味ではありません。要件を決め、結果を確認し、外部サービスの設定を行う作業は残ります。一方で、コードの調査・実装・修正・テストを会話で進められる点は、個人開発の進め方を大きく変えました。

## 開発環境にOrcaを使った理由

開発環境にはOrcaを使いました。リポジトリ、ターミナル、ローカル実行環境、ブラウザーでの画面確認を同じ作業場所で扱えるためです。

たとえば、次のような流れで作業しました。

1. Codexに機能追加を依頼する
2. ローカルのWorkers環境を起動する
3. ブラウザーで画面を確認する
4. レイアウトや挙動の問題を伝える
5. Codexがコードを修正する
6. テストと画面確認をもう一度行う

画面画像や動画を作るときも、本番サイトではなく、ローカルD1に架空データを入れて確認しました。これにより、実際のメールアドレスや予定、写真URLを公開素材に混ぜずに済みます。

## 全体構成：Cloudflare WorkerとD1

このアプリは、フロントエンドとAPIを同じCloudflare Workerで提供しています。永続データはCloudflare D1に保存し、HTML・CSS・JavaScriptはWorkers Static Assetsから配信します。

構成を文章にすると、次のようになります。

```text
スマートフォン / ブラウザー
        |
        v
Cloudflare Worker
  ├─ Static Assets：HTML・CSS・JavaScript
  └─ TypeScript API・認証
        |
        v
Cloudflare D1：SQLite互換データベース

外部サービス
  ├─ Google Calendar API
  ├─ Open-Meteo：天気・地名検索
  ├─ Wikidata API：施設の座標検索
  └─ OpenStreetMap：地図タイル
```

デプロイ設定は`wrangler.jsonc`にまとめています。Workerのエントリーポイント、Static Assets、D1のバインディング、互換性日付、Cron Triggerなどを設定し、Workerからは`env.DB`のようなバインディングでリソースへアクセスします。

データベースの変更はマイグレーションとして管理しました。機能追加のたびに既存データが残った状態で移行できるか確認できるため、後から機能を増やす個人開発でも扱いやすくなります。

SQLには値を文字列連結せず、`prepare(...).bind(...)`でパラメーターを渡します。入力値とSQL構文を分離することで、SQLインジェクション対策とコードの見通しを両立しています。

参考：[Cloudflare Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/)、[Bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/)、[D1 Worker API](https://developers.cloudflare.com/d1/worker-api/)

## Cloudflareの無料枠でどこまで動かせるか

2人が予定を登録し、必要なときに閲覧する用途であれば、現行のCloudflare Workers Free枠を前提にした構成で運用できます。

今回のアプリでは、次のようにデータ量を抑えています。

- 画像ファイルをアップロードしない
- 常時起動するサーバーを持たない
- 小さな共有データをD1に保存する
- 天気予報を毎回取得せず、日次でキャッシュする
- 不要なデータベース検索を避ける
- Cloudflare Accessで利用者を制限する

ただし、「無料で無制限」という意味ではありません。Workers、D1、Access、ログ、外部APIにはそれぞれ制限や利用条件があります。無料枠の上限や料金は変更される可能性があるため、公開時点の公式料金表とCloudflareダッシュボード上の使用量を確認する必要があります。

参考：[Workers料金](https://developers.cloudflare.com/workers/platform/pricing/)、[Workers制限](https://developers.cloudflare.com/workers/platform/limits/)、[D1料金](https://developers.cloudflare.com/d1/platform/pricing/)、[D1制限](https://developers.cloudflare.com/d1/platform/limits/)

## 天気予報：場所名を座標に変換する

天気APIは、基本的に緯度と経度を受け取ります。そのため、予定に入力された「東京ディズニーシー」や「京都駅」のような場所名を、天気APIへ渡せる座標に変換する必要があります。

今回のアプリでは、次の順番で場所を解決します。

1. 施設名をWikidataで検索する
2. 座標が見つからなければOpen-Meteo Geocoding APIで地名検索する
3. 緯度・経度を使ってOpen-Meteo Forecast APIを呼び出す
4. 最高気温、最低気温、天気コード、降水確率を表示する

旅行計画では、出発前日から帰宅翌日までを予報対象にしました。1日の中に複数の立ち寄り先がある場合は、立ち寄り先ごとに地域を解決し、それぞれの天気を表示します。

同じ場所の天気を何度も取得しないよう、予報はD1にキャッシュします。同じ日付の間はキャッシュを利用し、日付が変わった後の最初のアクセスで新しい予報を取得します。新しい取得に失敗した場合は、以前の予報を表示し、古いデータであることを示します。

Open-Meteoは個人・非商用利用向けの条件があります。実際に利用するときは、[Open-Meteoの利用条件](https://open-meteo.com/en/terms)と[Forecast APIの仕様](https://open-meteo.com/en/docs)を確認してください。

## 地図：Leaflet、OpenStreetMap、Wikidata

地図にはLeafletを使いました。Leafletは地図のパン・ズーム・マーカー表示を担当し、地図タイルにはOpenStreetMapを使います。施設名から座標を探す部分ではWikidataを使いました。

```js
const map = L.map("japan-map", {
  scrollWheelZoom: false,
}).fitBounds(japanBounds);

L.tileLayer("https://tile.openstreetmap.org/{z}/{x}/{y}.png", {
  maxZoom: 19,
  attribution: "&copy; OpenStreetMap contributors",
}).addTo(map);
```

地図をクリックしただけで保存済みの座標が変わらないようにし、記録を選択して配置モードに入ったときだけ仮マーカーを表示します。最後に保存操作を行った場合だけ、D1の座標を更新します。

この設計にしたのは、地図を拡大・縮小したり別の場所を見たりしただけで、思い出の位置が壊れる問題を防ぐためです。

OpenStreetMapの標準タイルは無制限の無料CDNではありません。帰属表示やタイル利用ポリシーを守り、アクセスが増える場合は利用規模に合ったタイル提供事業者を検討する必要があります。

参考：[Leafletリファレンス](https://leafletjs.com/reference/)、[OpenStreetMap Tile Usage Policy](https://operations.osmfoundation.org/policies/tiles/)

## Google Calendar連携

Google Calendar APIはOAuth 2.0で認可します。アカウントごとに表示名を設定し、複数のカレンダーから表示対象を選べるようにしました。

Google Calendar連携はアプリの主役ではなく、補助機能として別ページにまとめています。共有アプリ上で作った「2人の予定」と、個人の仕事・学校・私用予定を分けて扱えるようにするためです。

サイトで作成した共有予定は、連携済みユーザーそれぞれの同期先カレンダーへ登録できます。D1にサイト予定とGoogle上のイベントIDの対応を保存し、次回の変更では新規作成ではなく既存イベントを更新します。

GoogleのRefresh TokenはD1へ平文で保存せず、Web CryptoのAES-GCMで暗号化します。暗号鍵やOAuth Client Secretは設定ファイルやGitに書かず、Cloudflare Worker Secretsで管理します。

## 認証とセキュリティ

ログインは登録済みメールアドレスとパスワードで行います。パスワードはランダムソルトとscryptでハッシュ化し、平文では保存しません。

セッションCookieには次の属性を設定しています。

- `Secure`
- `HttpOnly`
- `SameSite=Lax`

D1にはセッショントークンそのものではなく、SHA-256ハッシュを保存します。ログイン試行にはIPアドレスとメールアドレス単位のレート制限を設けています。

GoogleのRefresh Token、OAuth Client Secret、パスワード、実際のメールアドレスは、Wrangler設定ファイルやGitリポジトリへ保存しません。Cloudflare Worker Secretsなどの環境側の安全な保管場所を使います。

また、記事や画面キャプチャには本番データを使わず、ローカル用D1へ架空データを投入しました。個人開発でも、公開用データと本番データを最初から分けておくことが重要です。

## AIに任せられること、任せられないこと

今回の開発でCodexに任せられたのは、コードの調査、実装、テスト、修正、リファクタリングでした。

一方で、次の判断は人間が行いました。

- どの機能を作るか
- どの情報を保存するか
- どの情報を外部APIへ送るか
- 本番とローカルをどう分けるか
- 認証情報をどこに保管するか
- 無料枠で運用できる規模か
- 外部サービスの利用規約に問題がないか

AIは実装の速度を上げられますが、仕様の正しさやセキュリティを自動的に保証するものではありません。型チェック、テスト、実画面の確認、外部サービスの公式ドキュメント確認は省略しないようにしました。

## まとめ

個人向けCodexの最小課金プランとOrcaを使って、コードを書かずに個人Webアプリを作る試みを行いました。

今回の構成では、Cloudflare Worker、D1、Google Calendar、Open-Meteo、Leaflet、OpenStreetMap、Wikidataを組み合わせています。個人利用の規模であれば、Cloudflareの無料枠を前提に運用できる構成にできます。

特に印象的だったのは、実装そのものよりも、要件の整理と確認の重要性です。予定や思い出をどう保存するか、どの情報を共有するか、外部APIが失敗したときどう表示するかを決めてからコードを書く必要があります。

AIによってコードを書く作業は大きく減らせます。しかし、作るものを決めること、結果を確認すること、秘密情報と個人情報を守ることは、引き続き人間の役割です。
